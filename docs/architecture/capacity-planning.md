# Capacity planning — Job Application Tracker

## 1. Цель

Оценить нагрузку на Job Application Tracker при 10 000 активных пользователей в сутки и рассмотреть рост до 100 000 пользователей.

Расчёты основаны на предположениях. Это предварительная оценка, а не результат нагрузочного тестирования.

## 2. Активность пользователей

Предположим, что один активный пользователь в среднем выполняет за сутки:

| Операция | Количество | Тип |
|---|---:|---|
| Поиск вакансий | 8 | Чтение |
| Просмотр вакансии | 4 | Чтение |
| Просмотр своих данных | 5 | Чтение |
| Создание отклика | 0,2 | Запись |
| Изменение статуса | 0,4 | Запись |
| Сохранение вакансии | 0,2 | Запись |
| Создание напоминания | 0,1 | Запись |

Это принятые для расчёта значения, а не измеренная статистика.

## 3. Количество запросов

На одного пользователя приходится:

- чтений: 8 + 4 + 5 = 17 в сутки;
- запросов на запись: 0,2 + 0,4 + 0,2 + 0,1 = 0,9 в сутки.

Для 10 000 пользователей:

- чтений: 10 000 × 17 = 170 000 в сутки;
- запросов на запись: 10 000 × 0,9 = 9 000 в сутки;
- всего: 179 000 запросов в сутки.

Соотношение чтений и записей — примерно 18,9:1. Это соотношение HTTP-запросов приложения. Одному HTTP-запросу может соответствовать несколько запросов к базе данных.

## 4. Средняя и пиковая нагрузка

В сутках 86 400 секунд.

Среднее количество запросов в секунду:

179 000 / 86 400 ≈ 2,07 RPS.

Для предварительной оценки примем пиковую нагрузку в 10 раз выше средней:

2,07 × 10 ≈ 20,7 RPS.

Коэффициент пиковости 10 — это предположение, которое нужно проверить измерениями.

## 5. Сетевой трафик

Примем средний размер ответа:

| Операция | Количество в сутки | Размер ответа |
|---|---:|---:|
| Поиск вакансий | 80 000 | 25 KB |
| Просмотр вакансии | 40 000 | 8 KB |
| Просмотр своих данных | 50 000 | 5 KB |
| Запросы на запись | 9 000 | 1 KB |

При этих предположениях приложение отправляет около 2,579 GB ответов в сутки, или около 941 GB в год.

Расчёт не учитывает входящий трафик, заголовки, статические файлы, обращения к внешнему API и резервные копии.

## 6. Хранение данных за 6 лет

Для расчёта принимается срок хранения 6 лет, или 2190 дней.

При создании отклика сохраняется сам отклик и первая запись истории его статуса. Поэтому в истории учитываются 4 000 изменений статуса и 2 000 начальных записей при создании откликов.

| Таблица | Новых записей в сутки | Записей за 6 лет |
|---|---:|---:|
| applications | 2 000 | 4 380 000 |
| application_status_history | 6 000 | 13 140 000 |
| saved_vacancies | 2 000 | 4 380 000 |
| reminders | 1 000 | 2 190 000 |
| Итого | 11 000 | 24 090 000 |

Примем средний размер записи вместе с предварительным запасом на служебные данные равным 1 KB.

24 090 000 × 1 KB ≈ 24,09 GB.

Для грубой оценки индексов, остальных таблиц и служебных данных применим коэффициент 2:

24,09 × 2 = 48,18 GB.

Добавим резерв 30%:

48,18 × 1,3 ≈ 62,63 GB.

Ориентировочная ёмкость основной базы данных — около 63 GB.

Две полные резервные копии потребуют ещё около 126 GB. Основная база вместе с двумя копиями займёт около 189 GB.

Это приближённая оценка. Реальный объём зависит от структуры строк, индексов, числа уникальных вакансий и политики резервного копирования.

## 7. Рост до 100 000 пользователей

При десятикратном росте активности получаем:

| Метрика | 10 000 пользователей | 100 000 пользователей |
|---|---:|---:|
| Запросов в сутки | 179 000 | 1 790 000 |
| Средняя нагрузка | 2,07 RPS | 20,72 RPS |
| Пиковая нагрузка при коэффициенте 10 | 20,7 RPS | 207,2 RPS |
| Исходящие ответы приложения | 2,579 GB/сутки | 25,79 GB/сутки |

При тех же предположениях база данных для 100 000 пользователей может занимать около 626 GB с резервом.

## 8. Стратегия масштабирования

### FastAPI

Backend проектируется как stateless-приложение. При увеличении нагрузки можно запускать несколько экземпляров FastAPI за балансировщиком.

Данные пользователя и отклики хранятся в PostgreSQL, а не в памяти отдельного экземпляра приложения.

### PostgreSQL

Для работы с базой данных планируется использовать:

- индексы по часто используемым полям;
- пагинацию для списков;
- пул соединений;
- проверку медленных запросов;
- анализ запросов с помощью `EXPLAIN ANALYZE`.

Реплики для чтения можно рассмотреть при дальнейшем росте. Для MVP они не обязательны.

### Redis

Redis используется для кэширования ответов внешнего API вакансий.

Ключ кэша должен учитывать параметры поиска, например запрос, фильтры, страницу и размер страницы.

Период свежести результата — 10 минут. После этого результат считается устаревшим, но может оставаться в Redis.

Срок хранения ключа — до 24 часов с момента последнего успешного обновления. Если внешний API недоступен, backend может вернуть сохранённый результат с признаком `is_stale: true`. После истечения 24 часов результат больше нельзя вернуть из кэша.

Redis может удалить ключ раньше из-за нехватки памяти. Поэтому срок до 24 часов — верхняя граница, а не гарантия хранения каждого результата.

### Внешний API

Для работы с внешним API нужны:

- ограничение времени ожидания ответа;
- ограниченное количество повторных попыток;
- ограничение частоты запросов;
- кэширование одинаковых поисковых запросов;
- защита от одновременного обновления одного ключа разными запросами.

При длительном отказе внешнего API backend не должен бесконечно повторять запросы.

## 9. Работа при отказе внешнего API

Если внешний API недоступен:

1. Backend проверяет, есть ли результат в Redis.
2. Если результат ещё свежий, backend возвращает его с `is_stale: false`.
3. Если результат устарел, но хранится в Redis не дольше 24 часов, backend возвращает его с `is_stale: true`.
4. Если результата в Redis нет или срок его хранения истёк, backend возвращает контролируемую ошибку `503`.
5. Работа с откликами, статусами и историей продолжается, если PostgreSQL доступен.

Если недоступен сам Redis, backend не сможет использовать старые кэшированные результаты.

## 10. Проверка расчётов

Расчётные значения сами по себе не доказывают, что система выдерживает такую нагрузку. На этапе тестирования нужно проверить:

- время ответа основных эндпоинтов;
- фактически достигнутый RPS;
- долю попаданий в Redis;
- количество обращений к внешнему API;
- время выполнения запросов PostgreSQL;
- поведение приложения при отказе внешнего API.

Для нагрузочного тестирования можно использовать k6 или Locust.
