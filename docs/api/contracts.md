
# REST API Contracts — Job Application Tracker

**Статус:** проектный контракт для согласования Frontend и Backend.  
**Версия:** v1  
**Backend:** Python + FastAPI  
**Frontend:** React + TypeScript  
**Формат:** JSON  
**Базовый префикс:** `/api/v1`

> Это спецификация планируемого API, а не подтверждение реализации. Все UUID, адреса и данные в примерах вымышлены. Статусы, правила идентификаторов и поведение Redis согласованы командой на уровне архитектуры.

## 1. Общие правила

- Для закрытых маршрутов: `Authorization: Bearer <access_token>`.
- Даты и время — ISO 8601 в UTC, например `2026-10-20T10:00:00Z`.
- Локальные идентификаторы пользователей, вакансий, откликов, напоминаний — UUID.
- Внешнюю вакансию идентифицирует пара `source` + `external_id`, оба поля — строки. Пример: `{"source":"hh","external_id":"12345"}`.
- Пагинация: `page` (от 1, по умолчанию 1), `per_page` (от 1 до 100, по умолчанию 20). Ответ списка содержит `items`, `page`, `per_page`, `total`.
- Пользователь получает доступ только к собственным сохранениям, откликам, истории и напоминаниям; `user_id` берётся из токена, а не из запроса.
- URL вида `/vacancies/{source}/{external_id}` использует **внешнюю** пару, а `/applications/{id}`, `/saved-vacancies/{id}` используют **локальный UUID** соответствующего ресурса.

### 1.1. Единый формат ошибок

```json
{
  "error": {
    "code": "VACANCY_PROVIDER_UNAVAILABLE",
    "message": "Vacancy service temporarily unavailable"
  }
}
```

`code` — стабильный машинный код, `message` — пояснение. Для ошибок валидации дополнительно может передаваться `details` с информацией о полях. В FastAPI потребуется согласовать обработчики исключений, чтобы формат не отличался от стандартного `detail`.

| HTTP | Когда используется |
|---|---|
| 400 | Недопустимый переход статуса или некорректная операция |
| 401 | Нет токена или токен недействителен |
| 403 | Нет доступа к ресурсу |
| 404 | Ресурс отсутствует или не принадлежит пользователю |
| 409 | Дубликат email, сохранения или конфликт состояния |
| 422 | Ошибка валидации полей |
| 429 | Превышен лимит запросов |
| 502 | Некорректный ответ внешнего провайдера |
| 503 | Провайдер недоступен и пригодного кэша нет |

## 3. Вакансии и интеграция с внешним API

### GET `/api/v1/vacancies`

**Доступ:** публичный.  
**Параметры:** `query` (обязательная непустая строка), `page`, `per_page`.

Пример: `GET /api/v1/vacancies?query=python&page=1&per_page=20`

**200 OK:**

```json
{
  "items": [
    {
      "source": "hh",
      "external_id": "12345",
      "title": "Python Developer",
      "company": "Example Company",
      "url": "https://example.com/vacancy/12345"
    }
  ],
  "page": 1,
  "per_page": 20,
  "total": 1,
  "is_stale": false
}
```

`is_stale: false` — данные актуальны по принятой политике свежести (из внешнего API или свежего Redis-кэша). `is_stale: true` — отдаются сохранённые ранее данные при сбое провайдера, и Frontend должен предупредить пользователя об их возможной неактуальности.

**503 Service Unavailable**, если провайдер недоступен и пригодного кэша нет:

```json
{
  "error": {
    "code": "VACANCY_PROVIDER_UNAVAILABLE",
    "message": "Vacancy service temporarily unavailable"
  }
}
```

Ошибки: `422 VALIDATION_ERROR`, `429 RATE_LIMITED`, `502 VACANCY_PROVIDER_BAD_RESPONSE`, `503 VACANCY_PROVIDER_UNAVAILABLE`.

### GET `/api/v1/vacancies/{source}/{external_id}`

**Доступ:** публичный. Параметры пути — идентификаторы вакансии во внешнем API.

Пример: `GET /api/v1/vacancies/hh/12345`

**200 OK:**

```json
{
  "source": "hh",
  "external_id": "12345",
  "title": "Python Developer",
  "company": "Example Company",
  "description": "Разработка сервисов на Python и FastAPI",
  "url": "https://example.com/vacancy/12345",
  "is_stale": false
}
```

Ошибки: `404 VACANCY_NOT_FOUND`, `502 VACANCY_PROVIDER_BAD_RESPONSE`, `503 VACANCY_PROVIDER_UNAVAILABLE`. При наличии пригодной сохранённой копии деталей допускается `200` с `is_stale: true`.

### Сопоставление внешнего ID и UUID

1. Результаты поиска и детали вакансий адресуются через `source` + `external_id`; Frontend не генерирует UUID.
2. Для сохранения вакансии или создания отклика Backend ищет строку `vacancies` по уникальной паре `(source, external_id)`.
3. Если строки нет, Backend получает нужные данные о вакансии и создаёт её с локальным UUID; при одновременных запросах исключает дубли с помощью уникального ограничения и безопасной вставки (например, `INSERT ... ON CONFLICT`).
4. `saved_vacancies.vacancy_id` и `applications.vacancy_id` ссылаются на локальный `vacancies.id`.
5. Если свежие данные у провайдера недоступны, но вакансия уже существует локально, Backend может использовать локальную запись; если данных нет, возвращает контролируемую ошибку.

## 5. Отклики

Все маршруты раздела требуют Bearer-токен. Создание записи означает **учёт отклика внутри Job Application Tracker**, а не отправку резюме работодателю через внешний API.

### POST `/api/v1/applications`

Запрос:

```json
{
  "source": "hh",
  "external_id": "12345"
}
```

Backend находит или создаёт локальную вакансию по `(source, external_id)` и использует её UUID.

**201 Created:**

```json
{
  "id": "ec4c0a10-c7db-4e74-8609-b6b0be222635",
  "vacancy_id": "5d1f2cc8-d2e1-4c7d-b74d-4f854274d839",
  "status": "applied",
  "created_at": "2026-10-20T10:00:00Z",
  "updated_at": "2026-10-20T10:00:00Z"
}
```

В одной транзакции создаётся отклик с начальным статусом `applied` и первая запись истории `old_status: null`, `new_status: applied`. Политика повторных откликов на одну вакансию одним пользователем должна быть отдельно согласована перед созданием ограничений SQL.

### GET `/api/v1/applications`

Параметры: `page`, `per_page`, необязательный `status` из согласованного набора статусов.

**200 OK:**

```json
{
  "items": [
    {
      "id": "ec4c0a10-c7db-4e74-8609-b6b0be222635",
      "vacancy_id": "5d1f2cc8-d2e1-4c7d-b74d-4f854274d839",
      "vacancy": {
        "source": "hh",

        "title": "Python Developer",
        "company": "Example Company"

      "created_at": "2026-10-20T10:00:00Z",
      "updated_at": "2026-10-20T10:00:00Z"
    }

```

**200 OK:**

```json
  },
  "status": "applied",
  "created_at": "2026-10-20T10:00:00Z",
  "updated_at": "2026-10-20T10:00:00Z"

```

### PATCH `/api/v1/applications/{id}/status`

Запрос:

```json
{
  "status": "hr_interview"
}
```

**200 OK:**

```json
{
  "id": "ec4c0a10-c7db-4e74-8609-b6b0be222635",
  "status": "hr_interview",
  "updated_at": "2026-10-21T10:00:00Z"
}
```

Статус отклика и строка истории обновляются **атомарно** в одной транзакции. Ошибки: `404 APPLICATION_NOT_FOUND`, `422 INVALID_STATUS`; правила запрета отдельных переходов, если будут нужны, требуется согласовать отдельно.

### Допустимые статусы

| Значение API и БД | Отображение в UI |
|---|---|
| `applied` | Отклик отправлен |
| `hr_interview` | Собеседование с HR |
| `technical_interview` | Техническое собеседование |
| `test_task` | Тестовое задание |
| `offer` | Предложение о работе |
| `rejected` | Отказ |

Этот список должен совпадать в React, FastAPI и PostgreSQL; добавление новых статусов требует согласованного изменения контракта и миграций.

## 7. Статистика

### GET `/api/v1/statistics`

**Доступ:** авторизованный пользователь.

**200 OK:**

```json
{
  "total_applications": 12,
  "by_status": {
    "applied": 5,
    "hr_interview": 3,
    "technical_interview": 2,
    "test_task": 0,
    "offer": 1,
    "rejected": 1
  }
}
```

Сумма `by_status` равна `total_applications` (учитывается **текущий** статус каждого отклика).

## 8. Redis и отказоустойчивость

- Ключ кэша формируется из нормализованных параметров запроса (`query`, фильтры при их добавлении, `page`, `per_page`) и источника данных; разные параметры не должны использовать одну запись.
- Проектная свежесть результата: **10 минут**. Допустимое хранение устаревшей копии для аварийного режима: **до 24 часов**.
- Физический TTL Redis должен позволять пережить период свежести: если ключ удаляется через 10 минут, при сбое вернуть старые данные будет невозможно.
- При успешном ответе внешнего API кэш обновляется и отдаётся `is_stale: false`.
- При недоступности провайдера, если пригодная копия существует, возвращается `200` и `is_stale: true`; иначе — `503` в едином формате ошибки.
- Сбои внешнего API не должны блокировать операции с уже сохранёнными откликами, статусами и историей, пока PostgreSQL доступен.
- В реализации нужны HTTP-таймауты, ограниченные повторные попытки, защита от параллельного обновления одного ключа и учёт лимитов внешнего API.
- Redis — кэш, не источник истины для пользовательских откликов.

## 9. Предварительные нефункциональные требования

Значения — **целевые p95 для серверного времени ответа**, ещё не подтверждённые тестами.

| Операция | Целевой p95 |
|---|---:|
| Регистрация и авторизация | ≤ 300 мс |
| Получение откликов | ≤ 300 мс |
| Изменение статуса | ≤ 300 мс |
| Статистика | ≤ 500 мс |
| Поиск из Redis | ≤ 200 мс |
| Поиск через внешний API | ≤ 2000 мс |

Подлежат проверке нагрузочными тестами с учётом сценариев из `docs/architecture/capacity-planning.md`.

## 10. Безопасность и согласование реализации

- Пароли сохраняются только в виде надёжных хешей, не передаются клиенту в ответах.
- Токены проверяются на Backend; доступ к чужим ресурсам запрещён.
- Секреты и настройки БД/Redis/провайдера хранятся в переменных окружения.
- Для ошибок авторизации, валидации и внешнего API используется единый формат `error`.
- Все команды разработки используют перечисленные здесь имена статусов и поля JSON.
- **Требует отдельного решения до миграций:** допустимы ли несколько откликов одного пользователя на одну вакансию; какие переходы статусов запрещены; политика удаления данных; конкретный провайдер вакансий и его лимиты.

## 11. Приоритет реализации MVP

**Обязательно для основного сценария:** регистрация/вход, поиск и детали вакансии, сохранение, создание отклика, список откликов, изменение статуса, история.  
**Следующий приоритет:** напоминания, статистика, расширенная фильтрация.
